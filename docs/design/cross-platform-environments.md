## Environment and task bindings

The controller owns the environment registry, model credentials, task database and evidence store. Each registered environment declares its platform and transport; connecting is lazy, so an unavailable environment does not prevent another environment from running. `environment_list` reports configuration and connection state, not readiness. `environment_doctor` checks the worker's actual operating system and tools. A platform mismatch rejects the connection.

An assessment snapshots its environment configuration. The root uses `default_environment`; native `task` accepts `environment_id`, otherwise inheriting its parent's binding. The binding is immutable. Deduplication includes environment identity alongside role and scope. Environment configuration changes reject further execution in that assessment rather than silently selecting another worker. Children may probe only their assigned environment; root may probe registered environments in the assessment.

For example, a Linux Ghidra specialist and a Windows debugger specialist can share an original PE artifact without sharing worker filesystem paths. Role permissions remain root/analyst/verifier; selecting an environment never grants permissions or activates an unavailable backend.

Before each child model request, an asynchronous worker preflight intersects the role's registry definitions with observed capabilities and platform requirements. Rig holds only that request while probing; root orchestration remains lazy, and cancellation drops the pending probe. A failed or timed-out probe leaves controller tools available and includes an explicit diagnostic and unavailable-tool requirements in the request. Tool execution checks the backend again, including the requested debugger engine and location-preserving minimization mode. An absent capability is denied before worker dispatch, even for a manually constructed call. Linux-only tools are excluded from Windows selections. Local configured Ghidra uses the controller; remote Ghidra requires a successful launcher/bridge/Java availability probe. Capability observations indicate availability, not successful analysis or completed acceptance.

The configuration has no top-level `[runtime]` section. Register transports under `environments.<id>.runtime` and select `default_environment`; an empty registry enables controller-only static analysis. Old single-runtime configuration is rejected without conversion. Workbench Docker CLI configuration lives under `[workbench].docker_executable`; generated workbench configuration registers a Linux environment named `workbench` while preserving other registered environments. Desktop initialization and health checks use the selected environment, so a configured Windows VM does not require Docker. `wukong doctor` reports each registered environment independently.

```toml
default_environment = "linux"

[environments.linux]
name = "Linux analysis"
platform = "linux"

[environments.linux.runtime]
backend = "docker"
docker_container = "wukong-worker"
```

Controller job/session references are qualified by worker identity and retain the worker's local resource ID separately. File registration keys include run, worker and path. Background job observations select the owner's bound environment and use the same evidence/notification pipeline as manual queries.

Installed native Windows workers use `runtime.managed_ssh`, containing `installation_id`, `user`, `port`, `identity_file`, `known_hosts_file` and `host_key = { algorithm = "ssh-ed25519", key = "BASE64_PUBLIC_KEY" }`. Obtain the actual public host key through independent VM fingerprint confirmation; scanning a host alone does not establish trust. The management user is `wkgm` followed by the installation ID's first 16 hexadecimal characters. Private keys remain on the controller. Paths resolve against the configuration directory and must be absolute after resolution, without relative aliases or SSH expansion tokens. The dedicated known-hosts file must contain exactly `wukong-worker-INSTALLATION_ID ssh-ed25519 BASE64_PUBLIC_KEY` and a final newline, matching the configured public key.

`runtime.ssh_host` supplies a literal IP/DNS hostname and `runtime.ssh_executable` selects the controller's OpenSSH client. The managed transport ignores user/system SSH configuration, pins the Ed25519 key, uses only the explicit private key and disables agent/X11/port forwarding, proxy commands, local commands and connection sharing. It sends a fixed relay marker rather than a Python/shell launch command. The native server independently forces its enrolled relay; the protocol handshake also checks the installation ID. Generic Linux SSH retains bridge-path quoting with explicit strict host checking and forwarding disabled. Tests of client argument validation and real OpenSSH `-G` configuration parsing are distinct from successful SSH/VM installation acceptance; the desktop connection importer validates public setup receipts and independently confirmed fingerprints, then saves a dedicated public host pin without importing private key contents. See the [Windows component guide](../../workers/windows/README.md). Registration performs no connection check; desktop media preparation remains unfinished.

Protocol 2 handshakes establish the installation ID, operating-system boot identity and worker code/backend content hash. The controller pins this identity on connection and persists it transactionally on first use by each assessment/environment. Reconnection or resume rejects a changed identity before execution. An optional `installation_id` in environment configuration also pins the registered installation. A daemon restart has a separate diagnostic ID; it does not imply an OS reboot or establish session survival.

Windows combines the OS loader's `KUSER_SHARED_DATA.BootId` sequence with the boot-entry GUID from dynamically linked `NtQuerySystemInformation(SystemBootEnvironmentInformation)`. A boot-entry GUID alone can survive reboots; the loader sequence distinguishes boots without wall-clock arithmetic, PowerShell/WMI or complete process visibility. The query reads only a 712-byte prefix of the [read-only user shared mapping](https://www.microsoft.com/en-us/msrc/blog/2022/04/randomizing-the-kuser_shared_data-structure-on-windows) and a 32-byte native response, validates lengths, Windows 10+ x86/x64 layout and nonzero entry identity, and fails closed on unsupported data. See Microsoft's [BootId definition](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-kuser_shared_data) and [native-query compatibility contract](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntquerysysteminformation). Current-machine/cross-process checks do not replace real VM reboot acceptance.

Production Windows environments require an exclusive 120-second run/controller lease with persistent increasing epochs. A separate transport renews used leases every 15 seconds, independently of model/debugger requests and the controller's own database heartbeat. Workers validate identity and fencing before durable receipt lookup; renewal does not change a business request's fingerprint. Expiry alone never proves process death: in-flight requests block takeover, and another run cannot acquire while owned sessions/jobs remain. Close and reconcile resources before release. Explicit trusted fixtures bypass production leasing, not identity checks.

For native managed SSH, the System service additionally owns the controller-facing fence. Its protected `metadata/lease-epochs/` journal reserves each new epoch before issuing a token, with an exclusive writer handle, canonical complete records and a limit of 100,000 new fences; renewals reuse the current epoch. The service validates the verified worker's readiness identity and rejects stale bindings/tokens before forwarding to Python or its receipt ledger. It substitutes a separate inner Python lease, so Python never issues the outer token. Renewal can proceed during a long request; release and expired takeover cannot proceed during an in-flight or transport-uncertain business request. Such uncertainty remains until the service's worker epoch is torn down. These admission checks retain Python resource checks. The standalone native process path additionally owns its System host and target descendants; complete execution routing and an update-safe idle barrier remain unfinished. Native resource work uses a separate mutex from lease state, so inspection and cleanup do not hold the renewal lock. Admission is rechecked after waiting for resource access; release and takeover use a nonblocking idle check and refuse while resource work is busy. The concurrency regression holds the resource lock while verifying renewal and both refused transitions.

Resource requests queue through Tokio's asynchronous mutex, so contention does not block all service executor threads. The synchronous service poll uses a nonblocking lock attempt and reports not-idle while busy. Shutdown awaits the resource lock after cancelling request tasks. A real-dispatch regression holds the resource lock, polls four queued requests and verifies that renewal still completes while release and takeover remain refused. Individual synchronous preparation/cleanup work is still serialized; managed debugger exchanges await outside the resource and input locks while the service retains the guardian Job and journal ticket.

The native service also opens a protected SQLite resource journal, reusing `rusqlite` and the existing binding/owner types. One active resource and pending mutation are reserved transactionally; interrupted effects survive database reopen and are reconciled rather than replayed. Active or uncertain entries additionally block lease release and expired takeover after service restart. Standalone process resources now use this journal, owned guardian Jobs and SDK profile/scratch cleanup. Fresh offline installation and the specified trusted preparation/host/service interruption cases passed at `69a5e3b`; see the [Windows component guide](../../workers/windows/README.md) for source-bound evidence and remaining limits.

Native resource discovery uses the protected journal, not the metadata worker's job directory. The leased `job.list` array and typed `resource.list` pages are run/binding scoped, bounded to 64 entries and ordered by resource ID; original owner/start-effect/specification hashes remain traceable across controller changes. Resource summaries omit specifications and environment values. Discovery is not a substitute for OS cleanup or the direct journal idle barrier. See the [Windows API contract](../../workers/windows/README.md).

## Shared and large artifacts

`artifact_stage` accepts a same-run evidence ID and stages a verified immutable copy in the caller's environment. Cross-environment transfer passes through the controller. The original evidence identity is retained. `stage_target` also streams its hash-verified original rather than placing the complete file in one RPC.

The worker exposes `file.upload.begin`, `file.upload.status`, `file.upload.write`, `file.upload.commit`, `file.stat` and `file.read`. Uploads are capped at 16 GiB, chunks at 1 MiB, and the existing RPC frame limit remains 48 MiB. Transfer identity binds destination, size, SHA256 and executable policy. Status is queried independently of cached begin receipts. Repeated or partially persisted chunks must match existing bytes; gaps and conflicting contents are rejected. Commit verifies size and full hash before atomic create-if-absent publication. Existing destination contents cannot be overwritten.

Large downloads verify each bounded chunk and the complete hash before streaming evidence ingestion. `file_get` returns metadata and an evidence ID, not inline file bytes. Model-facing output remains bounded. Actual free disk space is checked at upload preparation; an IO failure can still occur if other processes consume space. Reconnection does not replay unknown debugger mutations.

## Unified process launches

`job_start` accepts the existing schema-1 `launch_spec` with an optional staged `input`. Omit per-call argv, environment and cwd overrides; an explicit timeout must match the manifest. Process jobs support `stdin_pipe` and `argv_file` with `@@`, while PTY input belongs to interactive sessions. Raw process jobs also accept staged stdin. Dispatch requires observed `launch_spec_jobs` or `process_stdin` support before sending these new inputs to a worker.

Windows resolves the manifest and every declared member from completed native input receipts in the current owner scope. The fresh System host rereads the admitted manifest and checks its complete configuration against the protected request before preparing the persona. Members retain their logical layout and executable/data policies; a separately guarded writable cwd shares the existing resource directory and cleanup machinery. Native launches require offline service mode, reject Linux loader/library paths and allow at most 64 declared members plus an argv input. Manifest and protected request each fit 64 KiB; stdin fits 32 MiB and paths fit the cleanup depth limit. Internal process schema 3 binds the complete request hash into results; old active contracts fail closed. Cached start lookup still precedes new input resolution. Installed-VM qualification of the specified trusted process launches and service recovery passed at `6e2bc91`; the remaining execution routes are pending. See the [source-bound qualification](../../workers/windows/README.md).

Linux reuses its existing LaunchSpec resolver and UID isolation. It stages the complete declared layout, including files outside cwd, into sealed execution files and a separate writable working tree. Challenge preparation records regular cwd files in the manifest; symlinks are rejected and staging remains bounded to 1024 files/32 MiB. The documented container capabilities, read-only root and executable `/tmp` remain required.

## Structured debugger adapters

The builtin debugger currently uses GDB/MI. `mode = "dump"` requires a separate staged dump and forbids launch arguments; the staged target remains the run's original image. Inspection and control retain their bounded typed interfaces, stop/deadline handling and session ownership. Dump sessions reject execution control. Raw `debug_command` remains GDB/MI-only. The `dbgeng` selector is reserved for managed Windows admission; the Python metadata worker reports it unavailable and cannot create Windows debugger processes.

Windows debugging uses the pinned external WinDbg MCP tool and the existing rmcp protocol library. The custom DbgEng implementation and its Python protocol adapter have been removed. The controller's Rig/rmcp client passed actual x64/x86 dump/live interoperability in the dedicated VM. Native contained qualification calls the external tool using owned processes and retains raw MCP transcripts. Managed native launch routes now use the protected journal and paired target/debugger cleanup intents. Symbol/target correspondence, dump admission, negative fixtures and installed session/recovery acceptance remain unfinished; direct MCP interoperability does not establish production isolation. See [external debugger acceptance](../../workers/tests/README.md#external-windbg-mcp-acceptance).

## Windows offline delivery contract

The native offline bootstrap/service implementation is described in the [Windows component guide](../../workers/windows/README.md); the provided offline Windows 10 VM passed fresh installation, service/OS restart and contained trusted-fixture PDB qualification at `7b6c4c0`. Native target-execution admission and the complete offline repair/update/rollback/uninstall lifecycle remain incomplete. Registration does not establish production availability. The delivery contract requires a complete offline package assembled on the internet-connected controller from pinned, verified official payloads. The VM installer must include every required runtime, dependency and SSH/debugger installation payload and must never fetch missing components. Installation, repair, upgrade and rollback must work without VM internet access; the SSH management connection remains available. Symbols are prepared by the controller and staged into a local-only symbol cache.

The target backend is DbgEng with structured inspection/control, owned sessions and independent replay. The VM supplies the external isolation boundary; target permissions and metadata protections remain separate controls. Kernel debugging, VM creation, automatic snapshot management and GUI interaction are outside the first release. Real Windows VM acceptance is required before claiming Windows execution or offline installation support.

## State and validation boundary

New resource records require state schema 4. Old workspaces are rejected without migration; create a fresh workspace and retain old data separately. Unit/fixture checks exercise task binding, lazy connection, real bridge file transfer, resumable upload and evidence identity. They do not establish real GDB/Ghidra/DbgEng acceptance or Windows VM installer acceptance. See the [implementation contract](implementation-contract.md) and [worker guide](../../workers/runtime/README.md).
