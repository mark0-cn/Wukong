# Native Windows worker components

`native/resource_runtime.rs` connects standalone process `job.start/status/cancel/artifacts` and native output `file.get/stat/read` to the existing controller SSH fence. A start requires a stable matching request/call ID, an executable upload completed in the current owner scope, a `files/...` program and private cwd `.`. Bounded argv/environment/deadline/output options use a 16-process/1-GiB Job. The native journal is consulted before new input resolution, so a settled or interrupted start never launches again after a controller change. The service retains transferable owned kernel handles for the fresh System host; thread-affine desktops stay in that child. Its protected result, binary streams and original receipt are exposed after successful host Job drain and bound cleanup. Polling requests cancellation on lease expiry; service stop requests cancellation and waits up to 15 seconds for cleanup. Host/preparation errors retain the active journal blocker and report pending cleanup. The metadata broker stays health-only and complete production capability advertisement stays false. Launch bundles, preparation interruption, recovery/repair after failure, debugger/replay/interactive/shell/Python routing and full lifecycle acceptance remain unfinished. The provided Windows 10 VM passed 98 inert library checks with two explicit fixture skips; positive installed-System/controller process acceptance is pending.

`native/resource_process.rs` now implements the internal `resource-execute` System host. It shares signed-deployment verification, fixed environment setup and profile creation with startup qualification. Requests must occupy the exact protected `metadata/resource-requests/RESOURCE.json` slot and bind the current installation/package, controller owner and admitted executable reference. Inputs are verified before persona creation; the image is copied from the retained native input reader, keeps its logical `files/...` layout and receives a protected read/execute policy and no-write/no-delete sharing handle. Profile intent records the resource ID before profile creation. The host launches a zero-capability target through the existing suspended, Job-owned AppContainer path, then closes the persona and removes reclaimed scratch after successful drain. Cleanup errors remain errors; restrictive target-created descendants are not reported as removed. Standalone process fence/journal dispatch is connected; interruption during preparation, recovery after host failure and the other execution RPC paths are still pending. Ordinary management/metadata tokens cannot invoke this System-only entry. Its positive installed-VM execution acceptance is not yet complete.

`native/process_capture.rs` reuses the standard library's anonymous pipes and safe owned-handle conversion for independent binary stdin/stdout/stderr. Reader threads begin after synchronous profile/private-station setup. Combined retained output is limited to 1 KiB–8 MiB; overflow, deadline or cancellation stops and drains the same Job before joining I/O, and stdin reports actual bytes written and completion/error separately. Streamed analysis launches configure and read back aggregate Job memory (16 MiB–4 GiB), process count (1–64) and below-normal priority before the first instruction. A successful stop also waits for the held leader's process-object signal: Job active-process count can reach zero earlier during termination rundown. The provided Windows 10 VM passed trusted self-built fixture checks for binary stream separation, flooding, memory/process-limit enforcement, cancellation/deadlines and a descendant retaining an output writer. These fixtures do not replace the pending System-host/AppContainer and controller integration acceptance.

The internal resource journal now also reserves typed debugger-control and interactive-write effects for live resources. It checks the resource kind and run/worker binding, serializes pending mutations, preserves stable request fingerprints and rejects new work during closing or after closure. A completed mutation can be read again without beginning it; an interrupted mutation remains pending across reopen and becomes `uncertain_closed` only when the owning runtime supplies cleanup confirmation. Recovery can read the original start effect, owner, kind, specification and phase, including an old boot's outstanding intent. Missing/ambiguous start intents or changed payload fingerprints fail closed. These records describe persisted intent, not observed OS liveness or cleanup. The native runtime must validate the current controller lease before using them; standalone process RPC uses this journal, while the remaining execution paths are pending.

Startup qualification also includes a fixed self-DACL adversarial probe in each target/debugger AppContainer. After checking the actual zero-capability/traverse-only token, the sealed child uses its own process and thread pseudo-handles to replace both DACLs with a read-back-verified Everyone/full-access grant. It then requests ten process rights and nine thread rights individually against the still-live System resource host, including memory access, handle duplication, thread creation/context/token changes, termination and security changes; only `ERROR_ACCESS_DENIED` qualifies. No obtained right is exercised against another process. The System parent checks the reported PID/TID against its own current identities. Private-file, scratch/guard and correlated network checks run after self-DACL mutation, followed by the existing Job/profile/scratch cleanup. This tests specified boundaries despite mutable self-DACLs, not immutable process ACLs or complete adversarial isolation. The [pseudo-handle contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getcurrentprocess) and [security API](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo) explain the SDK mechanism. Production execution remains disabled.

The standalone Cargo package builds worker components without linking the desktop controller, WebView or model clients. `native/dbgeng.rs` is shared with the controller repository's development helper. The component package version is independent of the application release; the delivered worker identity also binds the actual source/binary contents and runtime protocol.

The helper reuses the existing `object` library for x86/x64 PE metadata, the explicitly configured SDK's `dbghelp.dll` [file-index API](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-symsrvgetfileindexinfow) for GUID PDB identity, and DbgEng's [module-information API](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/dbgeng/nf-dbgeng-idebugadvanced3-getsymbolinformationwide) for live/dump CodeView observations. Python owns correspondence policy, without another PE, minidump or MSF parser. File-index calls run on the helper's owning thread before DbgEng initialization; later file-index calls are refused, and failed engine initialization terminates the helper. Held file handles deny concurrent write/delete sharing and bind the observations to SHA256. PE inspection accepts regular files up to 256 MiB, at most 96 sections, 128 debug entries and one CodeView record of at most 64 KiB; PDB hashing streams files up to 4 GiB. Module correspondence requires the complete loaded-module list within 256 entries.

Correspondence compares mapped size, timestamp, mutually available checksums and supported RSDS GUID/age; a conflicting named module or ambiguous candidates fail. Missing CodeView is an explicit `module_metadata_only` gap. A match always records `byte_identity_verified = false`: module metadata does not establish equality of executable bytes. Symbols may come only from a simple, non-device filename directly in the configured cache; embedded producer directories, symbol servers and environment paths are ignored. A present PDB must have the expected GUID/age and content hash; missing symbols remain explicit. SDK file-index identity is separate from successful symbol loading, and images renamed to `.pdb` are rejected. The [trusted debugger fixtures](../tests/README.md) exercise both architectures and retain native format refusals and original transcripts. These checks do not qualify contained PDB loading, legacy full-user dumps, valid kernel-dump rejection or the unfinished production broker.

Every current service start generates a fresh 128-bit qualification ID and runs the sealed System resource host before worker/SSH readiness, including after a service restart in the same OS boot. Each receipt is created as `metadata/isolation-selftest-MANIFEST-QUALIFICATION.json`, without overwriting prior evidence. Historical manifest-only receipts never skip a probe. This uses the existing process/Job qualification path rather than another boot-identity implementation. The ordinary dependency self-test cache remains separate; fresh resource qualification does not establish production execution, lifecycle recovery or successful reboot acceptance. The dedicated acceptance entry requires a new qualification receipt on restart. The provided VM passed this check and OS-reboot qualification at `7b6c4c0`; the hosted fixture was not rerun.

The native library stages verified payloads into newly created directories with explicit protected Windows ACLs. It opens single-link regular source files without following a final reparse point or sharing write/delete access, verifies their signed size/hash through the held handle before creating a readable destination file, then hashes the copy and verifies the complete destination again. Manifest/public-key bytes come from verified in-memory identities; the held, bounded signature is verified against that manifest before staging. VM policies separate System/administrator metadata from readable executable contents. Source media and staging parents must remain private from concurrent writers; these checks do not provide general privileged collection from a target-writable directory. Failed staging remains caller-owned for transaction recovery. This module does not activate a version or create services/accounts. Ordinary Windows CI tests use only inert signed files and owner-only temporary directories; they verify real sharing conflicts, rename rejection, hardlink refusal, permissions and rejection of changed sources, relative roots and overwrites without installing anything on the development host.
