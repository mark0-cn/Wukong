# Native Windows worker components

English · [简体中文](README.zh-CN.md)

Windows execution requires a dedicated, disposable target VM. The target may affect the entire guest, including its worker. Configure host access, shared folders/devices and external networking at the hypervisor boundary; keep controller/model credentials and signing keys outside the guest. Retain original evidence on the controller and reset or discard the VM after untrusted execution. The worker does not create VMs, configure hypervisor policy or automate snapshots.

Signed enrollment requires `"execution_boundary": "disposable_vm"`. The signed record schema, signing CLI, offline media preparation, installer and service enforce this declaration. Missing, null or unsupported boundaries are rejected. Deployment targets a dedicated disposable VM; no migration or legacy-enrollment compatibility is provided. Offline baseline provisioning disables Windows Defender protection in that disposable VM before installation and snapshot creation, with no configuration switch. The boot wrapper applies the policies and uses the supported `Set-MpPreference` API to disable realtime/behavior/on-access/script/IOAV/first-seen protection and sample submission, verifying the resulting preference values with `Get-MpPreference`. It does not use protected service-control APIs or Tamper-Protected service-start writes, and does not modify the controller or other hosts. Restoring that fixed baseline removes subsequent sample-induced changes while retaining its reviewed Defender-disabled state.

Startup records deployment identity, resource recovery, dependency self-test, guest controls self-test and communication readiness as separate stages. Each stage publishes start and success/failure events with elapsed time and a stable error code. Protected `metadata/startup-diagnostics.json` uses schema 2, is atomically replaced, capped at 16 KiB, and bound to the installation, verified package/boot identity when available, and a fresh startup attempt. `last-service-error.txt` is refreshed for the same attempt, including pending/ready states. Fixed summaries omit arbitrary exception text. Installer failures include current diagnostic identity and code; hosted acceptance validates the full report separately from installation success.

The project no longer subscribes to or matches WFP events, and startup does not require loopback-block evidence. AppContainer/token, ACL, process ownership, cleanup and debugger checks remain guest controls. Fresh schema-5 qualification receipts use `scope: "disposable_vm_guest_controls"`. Reports and `doctor` declare `execution_boundary: "disposable_vm"` and `external_isolation_verified: false`; `doctor.guest_controls_verified` describes the current startup checks. These checks cannot certify hypervisor isolation or evidence integrity after guest compromise. Windows may still use its own WFP facilities internally; this change does not disable the OS firewall.

Unexpected stops in the sealed startup debugger fixture retain a bounded diagnostic projection in the protected host log: architecture, expected/observed addresses, exception flags and the first frame identity. Each selected string is limited to 192 identifier characters; arbitrary MCP output and target contents are omitted. The structured startup report still uses its fixed stage code and summary.

Hosted service-restart acceptance checks the bounded report and matching `startup_ready` text summary before and after restart, and requires a new startup attempt identity. The summary file's existence is not an error by itself; stale identity, pending startup and runtime-failure summaries still fail acceptance.

The sealed fixture may continue one live, first-chance, continuable native breakpoint whose exception and first-frame addresses match the current stop in `ntdll`, plus one WOW64 loader notification for x86. Offline export symbols can attribute the native loader break to a nearby export, so qualification does not require a particular OS function name or zero symbol displacement. Repeated stops, mismatched addresses, other modules/faults and stored crash contexts are rejected. Qualification still requires the fixture's own PDB-resolved breakpoint, registers and stack to match. This allowance is not used for ordinary targets. See Microsoft's [initial breakpoint](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/initial-breakpoint) description.

## Ownership and request flow

The native Rust worker is the sole Windows execution authority. Managed SSH invokes the fixed relay, which authenticates the enrolled SCM service through its named pipe. The service owns startup, qualification, recovery and shutdown; `native/rpc/worker.rs` routes the public API. There is no persistent Python metadata worker, inner Python lease, loopback worker endpoint or reverse broker-health channel.

| Component | Responsibility |
| --- | --- |
| Controller / Rig | Agent scheduling, roles, durable business requests, evidence and independent verification |
| `workers/protocol` | Shared identity, lease, error and capacity types; public JSON-RPC semantics |
| `native/core/` | Ownership identity and immutable resource types, independent of RPC, storage and OS APIs |
| `native/host/` | Installation, SCM lifecycle, verified runtime context and qualification |
| `native/rpc/` | JSON-RPC registration, transport, boot binding and controller/run fencing |
| `native/resources/` | One resource manager owns admission, operation tickets, journal and recovery |
| `native/executors/` | Process/session plans, owned execution observations and result adapters; no journal mutation |
| `native/artifacts/` | Lease-scoped immutable inputs, run/resource-scoped outputs and bounded protected IO |
| `native/isolation/` | Windows tokens, AppContainers, Jobs, ACL and process launch |
| External WinDbg MCP / Python | Debugging or bounded analysis inside owned resources; no independent worker authority |

RPC resolves registered handlers into resource operations before calling the manager; resources and artifacts never query the RPC registry. `executors/results.rs` validates and publishes process/replay observations, while the manager alone commits cleanup and journal transitions. Shell and analysis adapters own their response projection. The shared protocol provides typed outcome/cleanup observations; the native journal retains its stricter OS cleanup proof.

The public transport remains JSON-RPC 2.0. The controller uses `jsonrpsee`; shared Rust types use Serde. Private session messages use generated Prost protobuf and Tokio framing; the external debugger uses `rmcp`. Raw debugger replies remain hashed evidence instead of being reimplemented as a new debugger protocol. Linux retains its existing Python worker.

`ping` and `doctor` are answered natively. The service enables registered execution capabilities only after signed-package checks, outstanding-resource recovery, offline dependency checks and a fresh guest controls/debugger qualification for this service start. `doctor.readiness` explains this state. Historical qualification receipts cannot qualify a new startup. The registry advertises only callable native execution or isolated analysis methods; Linux GDB commands, raw debugger commands, AFL/QEMU, core-file snapshots and runtime preparation are not advertised on Windows. Crash triage uses the owned DbgEng session plus `crash_replay`/`input_minimize`; `poc_verify` replays argv/stdin only, and mapped module contents stay unconfirmed because a kernel-reported path is not a content hash.

## Fencing, capacity and durable state

The native worker owns one 120-second run/controller lease. The controller renews it over a separate transport every 15 seconds. Protected `metadata/lease-epochs/` records reserve monotonically increasing epochs before issuance, with an exclusive writer handle and a 100,000-epoch bound. Renewal preserves the fence. Identity and lease checks precede cached-effect access. Expiry requests cancellation and does not prove resource cleanup; active requests/resources prevent takeover or release.

`doctor.capacity.max_active_resources` is currently **1**, shared by jobs, persistent sessions and analysis helpers. The SQLite uniqueness constraint enforces this capacity. An occupied worker returns `resource_busy` before admitting a new effect. The controller classifies this as a definite rejected effect, never an unknown one, and directs the caller to inspect `resource_list`, then reuse or close/cancel the owned active resource before starting another. The controller uses a FIFO Tokio admission mutex and bounded retries; observation, close, cancellation and lease renewal remain available while a start waits. A live session must be closed before another resource can start. Transport failures and unknown outcomes are never automatically replayed. The controller business ledger and worker resource journal retain distinct responsibilities.

The resource journal uses schema **2** and rejects older databases without migration or deletion. Use a fresh Worker installation for protocol v3 and retain earlier installations/evidence. Explicit lifecycle variants prevent a process, session and recovery operation from simultaneously occupying the single slot. Input preparation runs outside the resource lock and retains its separate input lock; admission then revalidates the lease and capacity. The manager reserves and issues a ticket, starts the owned Tokio task outside its lock, and commits the original observation against that ticket. Startup, process draining and recovery waits retain ownership independently of the calling RPC. Queries and cancellation can inspect an unfinished start or failed cleanup; failure never releases the journal blocker.

Uploads are stored once in protected native storage. `file.put` accepts at most 32 MiB; resumable uploads use 1-MiB chunks and accept at most 16 GiB. Upload declarations, content SHA256, executable policy and published receipts bind the worker identity, run, controller and lease epoch. Duplicate chunks must match original bytes; status reports the native durable offset. Reads and execution require completed receipts. Inputs are copied into owned resource scratch only when a tool needs them; no ordinary-account file receipt can authorize System reads. Original attachments remain unchanged.

After controller recovery, a logical-path lookup in a later lease epoch may re-admit only the newest declaration from an earlier epoch of the same run and installation, and only with its completed receipt. The native worker rechecks the original receipt, immutable single-link bytes and executable policy, copies those bytes into the successor's protected scope, and publishes a new declaration, receipt and `Reference`. A stale `Reference` by itself never authorizes acquisition or triggers recovery. Other runs, changed bytes and missing receipts fail with contextual re-stage/recovery guidance rather than an unqualified filesystem error.

## Execution and analysis

`job.*`, `debug.*`, `interact.*`, `exec.run`, `py.run`, replay, minimization and verification use the same native resource lifecycle and journal. A repeated request resolves the original intent before accessing successor inputs. Cleanup failures retain ownership; interrupted execution remains unknown unless original evidence proves an outcome. Artifact access is run-scoped and retains size/SHA256 identity. Resource results describe their isolation; only `doctor` reports current service readiness.

With a LaunchSpec, replay, verification and minimization independently resolve the caller's admitted target and require its SHA256, size and executable policy to match the canonical LaunchSpec target. Distinct logical paths are accepted only for identical bytes; the protected replay request binds the canonical target path. Per-call replay arguments remain rejected because the LaunchSpec owns argv.

`runtime.profile` reads admitted content identities directly from protected native storage without occupying an execution slot. `debug.profile` and `interact.profile` observe only the session-owned process handle, retain the original evidence and return bounded previews. Unavailable observations remain unknown; mapped paths do not prove file hashes. Static binary declarations remain controller-owned.

`seccomp.analyze` invokes the packaged analysis code through a disposable AppContainer Python process. The helper consumes only admitted inputs, has a 120-second deadline and an 8-MiB output limit, and retains execution receipts/stdout hashes. It neither constructs the Python worker runtime nor owns leases, daemons, sessions or a second job ledger.

The current offline package does not ship pwntools, pyelftools or Unicorn, so cyclic-offset, libc-identification and emulation methods are not registered or advertised. Adding a capability requires its offline dependencies and callable-path acceptance.

### Native Python source jobs

`py.run` launches packaged CPython with fixed `-I -B -u -X utf8` options. Source is nonempty UTF-8, at most 256 KiB without NUL, stored as a sealed non-executable input. It permits at most 64 argv entries and an optional admitted target, a 10–3600-second timeout and 1-KiB–8-MiB output. The existing 16-process/1-GiB Job limits apply. Source never executes in the System service. Python syntax failures produce a failed job and original stderr; retries retain the original source-bound intent.

## Offline delivery and validation

The native installer runs the reviewed installation for both setup UI and unattended provisioning. The installer coordinates protected state, SSH configuration, Service Control Manager activation and publication of the public connection receipt. The UI handles confirmation and receipt export.

Build in an x64 MSVC environment. Keep model credentials and signing private keys on the controller. Install/uninstall acceptance belongs only on dedicated VMs or isolated runners, never over a developer's installation.

CI stages the exact payload and native binaries without controller keys; the operator finalizes the downloadable template with the controller key directory:

```powershell
python -m scripts.worker.toolchain --cache target/windows-offline-cache --download
python -m scripts.worker.build_native
python -m scripts.worker.media template --cache target/windows-offline-cache --native target/windows-worker-native --output target/windows-worker-media-template --version VERSION
python -m scripts.worker.media check --template target/windows-worker-media-template --report target/windows-worker-media-check.json
python -m scripts.worker.media pack --template target/windows-worker-media-template --version VERSION --output target/windows-worker-media
python -m scripts.worker.media finalize --template ABSOLUTE_TEMPLATE_DIRECTORY --keys ABSOLUTE_CONTROLLER_KEY_DIRECTORY --spec enrollment-spec.json --output ABSOLUTE_MEDIA_DIRECTORY --generate-ssh-key ABSOLUTE_SSH_PRIVATE_PATH
cargo fmt --manifest-path workers/windows/Cargo.toml --all -- --check
cargo clippy --locked --manifest-path workers/windows/Cargo.toml --all-targets -- -D warnings
cargo test --locked --manifest-path workers/windows/Cargo.toml --all-targets
```

`template` stages `payload/`, `binaries/{wukong-worker.exe,wukong-package.exe}`, the unsigned `manifest-draft.json`, `native-build.json` and `media-template.json`; `check` then finalizes that template in a temporary directory with an ephemeral key and runs `WukongWorkerSetup.exe verify-enrollment`, so CI proves sealing, enrollment and media wiring without elevation or installation. Release builds publish the deterministic archive `wukong-windows-worker-media-<version>.zip`; verify it against `SHA256SUMS` and unpack it outside the key directory.

`finalize` requires an absolute controller key directory outside the template and output. The enrollment spec (`schema: 1`) provides a 32-character lowercase hexadecimal `installation_id`, an `environment_id` of 1–64 ASCII letters/digits/underscores/hyphens, `generation` (default 1), an IPv4 `management_peer` (loopback, unspecified, multicast and broadcast addresses are rejected), `ssh_port`, optional `execution_boundary` (only `disposable_vm`) and either a canonical `ssh_public_key {algorithm, key}` or `--generate-ssh-key`. SSH key generation uses the packaged `ssh-keygen.exe`; the private key is written outside the media and only the public key enters the signed enrollment. Finalize seals the staged payload, signs enrollment, bundles public media (`WukongWorkerSetup.exe`, `setup.json`, `payload/`, `enrollment/`, optional `recovery/`) and writes a hashed `media.json` receipt. It fails closed when the key directory or any private-key filename would appear inside the template or output. Never copy the controller key directory, SSH private keys or model credentials into the media or the guest.

Any Windows host can pre-check finalized public media without elevation: `WukongWorkerSetup.exe verify-enrollment <payload> <enrollment> <controller-public-key-hex> <controller-version>`. Installation uses the elevated `WukongWorkerSetup.exe install-reviewed setup.json <controller-key-hex> <sha256-of-enrollment.json>` and belongs only on the dedicated disposable VM.

When `install-reviewed` finds a valid existing deployment, it permits an upgrade only from the reviewed offline SYSTEM boot path. To authenticate that existing installation, this transition accepts a fully signed and hash-verified package with an older runtime protocol no newer than the installer; a newer unknown protocol remains rejected. The incoming candidate and every normal service/resource activation must still match the current protocol exactly. The signed candidate must have a newer semantic package version and enrollment generation while retaining installation, controller authority and SSH peer/port/client-key bindings. The installer stages and verifies the signed package, then updates protected enrollment/binding/deployment records, the stable SSH relay, the existing installation-scoped firewall rule and the existing owned service. Parent directories and replaced records are verified against their own explicit ACL policies; a binding file's narrower policy is never reused for the code root. Firewall verification accepts both the bare enrolled address and Windows Firewall's equivalent single-host subnet-mask readback, while retaining exact program, port, direction, action, profile and enabled-state checks. It never adopts a foreign service/rule or exposes an update RPC to model-driven execution. Any interrupted post-admission mutation fails the attempt: restore the old VM base rather than resuming a partial native upgrade in place.

### Installation result and re-saving

Successful offline setup writes the public `C:\ProgramData\WukongWorkers\<installation_id>\connection.json` receipt (schema 1, `receipt_version: 2`). It contains the installation/environment identity, the SSH user and port, the SSH host key and its fingerprint, and `candidate_addresses`: this guest's non-loopback IPv4 addresses, with RFC 1918 private addresses first and numeric ascending order within each group, de-duplicated and capped at 8. Candidate enumeration is best effort; a guest whose adapters cannot be read still completes the installation with an empty list. The protected record under ProgramData remains authoritative; the exported file is a public connection hint and never proves reachability or hypervisor isolation.

After success, setup offers **保存安装结果 / Save install result** and opens the Windows save dialog with the default name `wukong-worker-<installation_id>.json`. If the dialog cannot open or the selected path cannot be written, the same bytes are copied to `%USERPROFILE%\Desktop\wukong-worker-<installation_id>.json` (or `%PUBLIC%` or its Desktop when the profile is unavailable or has no Desktop) and setup reports the actual path. Saving never changes installation success: the protected record in ProgramData is already complete.

Starting setup with no arguments on a guest that already has a valid installation does not reinstall it. It shows a short "already installed" dialog and offers to save a refreshed result: the current adapter addresses are re-enumerated and only `candidate_addresses` changes, while the installation ID, SSH and host-key fields stay identical. Use this export after a guest address change instead of resetting the worker. Installation and repair still require the offline media and the reviewed `install-*`/`verify-enrollment` paths; the refresh flow performs no installation, service or firewall change.

Native build identity includes the shared protocol crate, native/Python sources, locked inputs and build scripts. Assembly verifies this identity and preserves dependency licenses. Enrollment pins the controller signer and installation; SSH independently pins the worker host key. Use the [cross-platform environment guide](../../docs/design/cross-platform-environments.md) for connection and task binding, and [worker acceptance guide](../tests/README.md) for installed process/debugger/recovery fixtures.

Unit tests establish contract and ownership invariants; they do not establish VM isolation or live-model effectiveness. Installed acceptance must match the exact signed source/package and include the normal Wukong discovery/dispatch path. The [2026-11-15 v3 acceptance record](../../docs/history/validation/2026-11-15-execution-contract-v3.md) binds the fresh installation, x64/x86 execution/debugging, restart recovery and complete Wukong workflow to their exact source/package and original evidence. Earlier [historical records](VALIDATION-HISTORY.md) retain their own commits, failures and limits, including unfinished maintenance and adversarial acceptance; those limits are not superseded by normal-path acceptance. Kernel debugging, automatic VM creation/snapshots and GUI target interaction remain outside this worker contract.

Windows Python sources are selected by `python-components.json`: the independent [analysis package](../analysis/README.md) and `python/selftest.py`. Helpers need only CPython standard libraries; `python/requirements.txt` is separate from Linux bridge dependencies. Offline packaging neither installs nor copies Linux worker modules. The signed source identity includes the analysis package and component inventory.
