# Native Windows worker components

English · [简体中文](README.zh-CN.md)

The standalone Cargo package builds worker components without linking the desktop controller, WebView or model clients. `native/dbgeng.rs` is shared with the controller repository's development helper. The component package version is independent of the application release; the delivered worker identity also binds the actual source/binary contents and runtime protocol.

From an x64 MSVC Native Tools shell at the repository root:

```powershell
python -m scripts.worker.build_native --check
python -m scripts.worker.build_native
cargo fmt --manifest-path workers/windows/Cargo.toml -- --check
```

The builder uses the committed standalone lockfile and an explicit static CRT setting. Outputs stay under `target/windows-worker-native` by default. Before writing `native-build.json`, it inspects both normal and delay-loaded PE imports and rejects dependencies on external Visual C++/Universal CRT libraries. This check applies to the bootstrap binaries themselves; the offline bundle must separately include all dependencies and original installation payloads of third-party tools. Building performs no installation, service registration or target execution.

The implementation follows [Rust CRT linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes) and Microsoft's [PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format). Windows CI formats and checks the standalone crate, builds its bootstrap binary and verifies its imports; automation tests also reject dynamic CRTs, invalid library names and malformed ordinary/delay-import tables.

The native library stages verified payloads into newly created directories with explicit protected Windows ACLs. It opens single-link regular source files without following a final reparse point or sharing write/delete access, verifies their signed size/hash through the held handle before creating a readable destination file, then hashes the copy and verifies the complete destination again. Manifest/public-key bytes come from verified in-memory identities; the held, bounded signature is verified against that manifest before staging. VM policies separate System/administrator metadata from readable executable contents. Source media and staging parents must remain private from concurrent writers; these checks do not provide general privileged collection from a target-writable directory. Failed staging remains caller-owned for transaction recovery. This module does not activate a version or create services/accounts. Ordinary Windows CI tests use only inert signed files and owner-only temporary directories; they verify real sharing conflicts, rename rejection, hardlink refusal, permissions and rejection of changed sources, relative roots and overwrites without installing anything on the development host.

An explicit read-only media fixture can copy a sealed payload into a new temporary directory and reverify it, without executing any payload or registering OS resources. Mount only the intended ISO read-only and independently select its public key; replace the placeholders below. The test does not mount/unmount media or perform VM installation acceptance.

```powershell
$env:WUKONG_STAGE_TEST_SOURCE = 'X:\payload'
$env:WUKONG_STAGE_TEST_PUBLIC_KEY = 'PINNED_CONTROLLER_PUBLIC_KEY_HEX'
$env:WUKONG_STAGE_TEST_CONTROLLER_VERSION = 'CONTROLLER_VERSION'
cargo test --locked --manifest-path workers/windows/Cargo.toml --lib stages_explicit_read_only_offline_media_without_execution -- --ignored
```

`wukong-worker.exe verify-package DIRECTORY PINNED_PUBLIC_KEY_HEX CONTROLLER_VERSION` uses the shared [offline package contract](../package/README.md). This read-only command verifies independent trust, compatibility and exact file contents. `verify-enrollment PACKAGE ENROLLMENT_DIRECTORY PINNED_PUBLIC_KEY_HEX CONTROLLER_VERSION` also verifies the public enrollment signature and payload binding. Neither verification command installs or activates a worker. The executable is included in static CRT checks alongside `wukong-dbgeng.exe`.

`toolchain.lock.json` pins official Python, OpenSSH, Python wheels and the full Debugging Tools MSI/CAB inventory by size and SHA256. The OpenSSH version in this lock is an upstream **preview**. Prepare the cache on the controller:

```powershell
python -m scripts.worker.toolchain --cache target/windows-offline-cache --download
python -m scripts.worker.toolchain --cache target/windows-offline-cache
python -m scripts.worker.layout --cache target/windows-offline-cache --output target/windows-offline-layout
```

Only `--download` permits network access. Existing mismatched cache entries fail instead of being replaced. Layout requires a Windows controller and a new output directory; it has no network/download path. It reads MSI tables in read-only mode, extracts only callback-approved CAB members, verifies the complete debugger payload inventory against metadata inside the pinned Microsoft bootstrapper, and preserves all original MSI/CAB/ZIP/wheel files and licenses. It does not run MSI installation/custom actions or modify installed tools. The extraction uses Microsoft's [MSI database](https://learn.microsoft.com/en-us/windows/win32/api/msiquery/nf-msiquery-msiviewfetch) and [cabinet callback](https://learn.microsoft.com/en-us/windows/win32/setupapi/spfilenotify-fileincabinet) APIs.

The output contains a private embeddable Python runtime with pre-unpacked wheels, Python worker sources, OpenSSH and the full SDK debugger file tree. Python ignores user/registry paths and loads only its shipped library and worker directories; the VM needs no pip. Archive paths reject links, traversal, aliases and overwrites. Use controller-private cache/staging directories: these checks do not provide concurrent-writer isolation. A failed output is retained for diagnosis and must not be reused. This command produces an **unsigned controller layout**. Ordinary controller layout checks and trusted fixtures do not establish clean Windows VM dependency coverage.

To assemble and sign a new complete payload, first commit the worker changes and rebuild from that clean commit. The assembler requires matching source revision/tree hashes, locked native build metadata, actual binary hashes and static CRT imports. It includes native binaries, their dependency license texts, the Rust standard-library copyright notice and all original third-party payloads. It never downloads missing files.

```powershell
$keys = Join-Path $PWD 'target/controller-signing'
./target/windows-worker-native/x86_64-pc-windows-msvc/release/wukong-package.exe key $keys
python -m scripts.worker.assemble --cache target/windows-offline-cache --output target/windows-worker-package --keys $keys
```

The key command prints only the public key/fingerprint for independent enrollment. Private key storage stays on the controller outside the package, protected as described in the [package contract](../package/README.md); the example uses a local development directory. `wukong-package.exe` is a controller utility and is excluded from the VM payload. The signed output binds complete files and compatibility, but still requires dependency/self-tests, the native installer/service/broker, desktop delivery/enrollment and real offline VM acceptance before production installation support can be claimed.

For a prepared public enrollment draft, `wukong-package enroll PACKAGE DRAFT ABSOLUTE_KEYS NEW_ABSOLUTE_OUTPUT CONTROLLER_VERSION` verifies the package with the controller's protected signing identity, checks the signed enrollment/payload binding and creates only public enrollment records outside the payload. The [enrollment contract](../package/README.md) describes the fields and initial-trust boundary. This command does not create VM accounts, install services or enroll SSH automatically.

The native builder also compiles known x64/x86 probes and matching PDBs using the controller's MSVC toolchains and static CRT. They are hash-bound to native build metadata and copied into the signed package. The guest needs no compiler. After native signature/tree verification against the independently enrolled key, the operator/installer can run the packaged Python entry:

```powershell
./target/windows-worker-package/runtime/python/python.exe -B ./target/windows-worker-package/runtime/worker/worker_selftest.py --package target/windows-worker-package --state target/windows-worker-selftest
```

The native caller must establish package trust first and protect the version directory from writers. This entry is never a worker RPC or a replacement for signature verification. It checks shipped probe hashes before execution, exercises OpenSSH key generation without network access, and runs x64/x86 dump/live inspection and three replay trials per architecture through the packaged runtime. The fixed SSH probe additionally receives the required Windows `ProgramData` path; target job environment filtering is unchanged. Temporary dummy SSH keys are removed; logs/results stay outside the signed tree. A successful report explicitly covers offline dependencies and trusted fixtures, not production target isolation or service/SSH installation. Verify the signed tree again after running it.

The debugger component is the structured DbgEng helper. Its real x64/x86 trusted-fixture acceptance is separate from production broker isolation and offline VM installation acceptance. The fixture suite also exercises replay with distinct producer/verifier IDs, three fresh process/working-directory trials per architecture, exact input/target hashes and an observed `0xc0000005` exception. This establishes the trusted replay path, without claiming production metadata protection or exploitation impact. See the [cross-platform environment contract](../../docs/design/cross-platform-environments.md) and [runtime guide](../runtime/README.md).

After opening a dump or attachment, the helper checks the engine's actual debuggee class before enabling inspection. Only Windows user-mode sessions and user-mode small/full dumps are accepted. Kernel and other classes are rejected; any failed open invalidates and closes the helper so partially opened state cannot be reused. The fixture suite records the observed user-mode class/qualifier for x64/x86; a real kernel-dump rejection fixture remains outside current acceptance.

The native VM bootstrap and SCM service have callable implementation paths. Prepare fresh public setup media from a sealed payload and matching signed enrollment:

```powershell
python -m scripts.worker.bundle --package ABSOLUTE_PACKAGE --enrollment ABSOLUTE_PUBLIC_ENROLLMENT --output NEW_ABSOLUTE_MEDIA --public-key PINNED_CONTROLLER_PUBLIC_KEY_HEX --controller-version CONTROLLER_VERSION --verifier ABSOLUTE_NATIVE_WORKER_EXE
```

Media contains `WukongWorkerSetup.exe`, `setup.json`, `payload/` and two public enrollment records, without controller private keys. Transfer it to a dedicated Windows test VM; never install over the developer host. Setup reviews the version, installation, allowed controller address, SSH port and signing fingerprint. Initial owner trust requires independently comparing that fingerprint with the controller. Elevation re-verifies the exact reviewed enrollment and full payload before creating OS resources. The current native bootstrap UI is English. Preparing media is not installation acceptance.

Already-elevated automation in a dedicated test environment can run `WukongWorkerSetup.exe install-reviewed ABSOLUTE_SETUP_JSON PINNED_CONTROLLER_PUBLIC_KEY_HEX REVIEWED_ENROLLMENT_SHA256`. Supply the independently pinned controller key and SHA256 of the exact canonical `enrollment.json` reviewed on the controller. It applies the same verification and installation path, returns a JSON receipt, displays no dialogs and never elevates itself. This command is an operator entry point, not a worker RPC; do not run it over the developer's installation.

After successful setup, copy only the public `connection.json` back to the controller. In **Workspace settings → Environments → Register Windows VM**, import it, enter the VM address, select the existing controller private key and independently enter the host fingerprint shown by setup. Preview validates the installed-receipt shape, Ed25519 key/fingerprint, installation account and existing key-file path; it does not read private key contents, create files or contact the VM. Duplicate environment IDs are rejected. Adding to the draft preserves other configuration edits and comments. Saving creates an LF-terminated, content-named public host-pin file under controller settings, refusing to overwrite different contents. Cleanup tracks that exact public file; the selected private key stays external. An unfinished connection survives closing settings and must be added or reset before saving. The first environment becomes the default automatically. Registration is separate from connectivity and production isolation checks; desktop media preparation and complete VM lifecycle acceptance remain unfinished.

Before service creation, the fixed host-key generation and SSH configuration checks retain System/administrator-only `metadata/install-tool-ssh-keygen.log` and `metadata/install-tool-sshd.log`. Errors identify the failing executable; the SSH syntax check emits verbose diagnostics without listening. The hosted fixture includes only the last 4 KiB of each of these two fixed logs in its public report. Private keys and other metadata are excluded.

Elevated installation tools and the System SSH daemon use a fixed seven-variable Windows environment: `SYSTEMROOT`, `WINDIR`, `PROGRAMDATA`, `COMSPEC`, `PATH`, `TEMP` and `TMP`. Paths derive from Windows locations; shell lookup is limited to the Windows directory and System32. Their temporary directory is protected `metadata/system-tmp`, verified before launch and activation. The ordinary worker keeps its separate `data/tmp`; controller/provider environments are never copied wholesale into elevated children.

For an SSH syntax-check access violation, the dedicated hosted fixture also compares minimal and fixed Windows-runtime environments, then uses the sealed SDK CDB to inspect only the fault instruction pointer, a stack without arguments and module identities. Probes keep the existing executable network blocks and an empty local symbol directory. No memory dump is created. The report excludes full register displays, private key bytes and output outside the requested debugger sections; bounded diagnostic output does not establish successful installation.

Installation creates separate management, metadata-worker, debugger and target accounts, records ownership under the Windows ProgramData known folder and stores generated worker passwords in LSA. Interactive/RDP logons are denied; only broker-owned accounts receive batch-logon rights. The service verifies its active signature/tree and own executable, then starts ordinary-account Python on a private desktop with all enumerated privileges removed. Explicit process attributes place children in a non-breakaway Job before execution and inherit only input/log handles. An exiting worker epoch kills its descendants before the service stops. Fixed dependency self-tests gate first readiness and retain System/administrator-owned, manifest-bound receipts; their scope remains trusted fixtures.

Shipped SSH uses its own host key, public-key-only authentication, the enrolled controller address and a fixed native relay that ignores requested commands. Forwarding, TTY and user startup hooks are disabled. A native firewall rule limits peer, port and executable. Pipe ACLs exclude client server-instance creation; each frame checks the actual Windows caller SID, and the relay checks the server PID against SCM before sending data. The loopback endpoint token stays in protected worker state. Native binding covers the whole sealed manifest. Existing installations/services/account names fail rather than being adopted or overwritten; interrupted records remain for explicit repair.

The `ssh/` directory is System/administrator-only from creation, so host-key generation never exposes the private key while file permissions are being finalized. The management-readable public authorization file is separate at `bootstrap/authorized_keys`. Before activation and at service startup, deployment verification checks these directory/file ACLs, including both generated host-key files and the server configuration.

Firewall registration resolves the sealed executable to a local, normalized Windows path. Failures identify the COM property or registration stage; registration errors include the public executable/port/peer/profile settings. A local test exercises actual COM property setters/getters on an unregistered rule and verifies path identity, without adding or changing any host firewall rule. Actual registration remains a dedicated-VM acceptance check.

SCM service registration and fixed native child launches use the same local path normalization, keeping service ownership comparisons consistent with the verified executable. Offline DbgEng probe failures retain a bounded helper exit/loader reason in the protected self-test log. Such diagnostics do not relax ordinary-account privileges or turn a failed self-test into readiness.

Validation of packaged DbgEng helper/engine paths uses existing absolute local-drive names and checks every ancestor for links/reparse points before hashing or loading. It rejects network paths, alternate streams, relative traversal and ambiguous trailing dots/spaces. It avoids strict normalized-name queries: a real current-user fixture with every token privilege removed reproduces access denied from Python's strict path resolution while ordinary reads and the new checks succeed. The helper applies the same local-path policy. No privilege is restored. These checks rely on protected package/session directories and do not replace native broker ingestion of target-writable paths or real installed-worker acceptance.

Account creation resolves the builtin Users alias by its well-known SID and adds the owned account by SID, avoiding localized group-name assumptions. Early recovery is deliberately limited to an interrupted management-account create before payload/data/service activation. Add `--previous-package ABSOLUTE_PREVIOUS_PACKAGE --previous-enrollment ABSOLUTE_PREVIOUS_PUBLIC_ENROLLMENT` when preparing new media to include the original public signed proof. Recovery compares that proof with the protected intent, requires a higher signed enrollment generation and preserves accepted recovery generations. It also checks the exact owned-account comment, ordinary privilege and SID without resetting its password. Other existing accounts and later installation phases are refused by this path. Owner fingerprint review remains required before first activation.

Before creating accounts, bootstrap persists the complete signed first-owner enrollment in System/administrator-owned `metadata/authority.json`. Recovery and service startup take their signing key from that protected record; a matching manifest hash cannot authorize a replacement signer. Accepted recovery records retain their increasing high-water mark across interruptions, and startup requires the active enrollment to match the highest accepted record. Signature changes, stale/reused envelopes and noncanonical admission filenames are rejected. An interrupted development bootstrap containing only the original intent still needs its original signed proof and independent owner fingerprint review to establish this first authority; this narrow path does not adopt an existing installed worker or implement general migration. Failed-update rollback needs a separate authorized activation receipt and remains subsequent lifecycle work.

The service's `lease_proxy` owns controller-facing run fences and keeps its increasing epoch journal in System/administrator-only metadata. It verifies the readiness installation/boot/package identity, validates each fence before forwarding, and substitutes a separate Python lease without disclosing that inner token to the controller. Long calls do not block renewal. In-flight, cancelled or transport-uncertain business calls prevent release/expired takeover; uncertain calls remain an idle blocker until worker-epoch teardown. The journal allows 100,000 new fences without overwriting records; renewal does not consume a record. Inert local fixtures check real protected files, concurrent-writer rejection, restart persistence, stale admission, delayed renewal and cancellation. They use a controlled upstream adapter, not an installed VM service. Native target-resource ownership and the complete maintenance idle barrier still require the broker and VM acceptance.

Successful service stop and offline self-test acceptance explicitly terminate each owned Job and wait up to 10 seconds for its active-process count to reach zero. An exited leader does not prove its descendants exited. A drain failure prevents a successful lifecycle result or self-test receipt; destructor cleanup remains a best-effort error fallback. SCM stop-pending reports retain a wait hint and progress checkpoints while the worker and SSH Jobs drain. A local trusted fixture leaves a live child after its leader exits and verifies the Job barrier terminates that child. This checks process ownership, not installed-service or target-isolation acceptance.

Current development checks cover real local pipe identity/rejection, protected inert staging, signed recovery admission and native Job containment/termination of an actual descendant. They create no accounts, services or firewall rules on the host. The first offline VM attempt stopped at ordinary-account validation before service/firewall creation; clean completion remains pending. SSH connectivity, lifecycle recovery/updates/rollback and the target-isolation broker remain required acceptance/implementation work. Production target execution remains disabled; this bootstrap does not establish production Windows support.

Opt-in hosted installation acceptance uses `tests/acceptance/check_windows_worker.py` and its PowerShell helper. Both reject developer/self-hosted environments before global effects. The fixture acquires assets as a controller, seals media with temporary controller-only keys, then blocks external addresses for shipped executables at media/installed paths while retaining management to an assigned address on the same test machine and the CI agent's connection. It exercises the actual native installer, ordinary-account self-tests, the Rust controller's pinned SSH transport, immutable file transfer, stale fences and a service restart with increasing epochs. Only the bounded public report is uploaded. Cleanup checks exact service paths, ownership comments, firewall descriptions and installation intent before removing fixture resources; remaining temporary LSA secrets retire with the disposable VM. This is not production uninstall, whole-VM disconnection, Windows 10 VM or target-isolation acceptance. A configured pipeline is not a passed run; inspect its actual report and outcome.
